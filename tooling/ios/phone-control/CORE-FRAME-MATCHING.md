# CoreDevice 画面复核的有限容差

本补丁处理 ADDENDUM-08 §3.2。`IOSPhoneScreen.revalidate` 仍只消费本次
owner/session/epoch 的最新观察，原观察最多 120 秒，批准后取得的不同 native
frame 最多 30 秒，方向、尺寸必须一致。成功只返回新 frame；失败也不恢复旧观察。
这些条件和 Rust 的原生帧消费门没有放宽。

## 为什么不用单个全图亮度阈值

仅统计 `|Δ亮度| > 24` 的像素，会把 400×300 的纯白 255 整图改成灰色 240
算作零个变化像素。等亮度改色也有同类盲区。这里保留 sRGB 解码 RGBA，
**任何通道有任何字节差异，都计入面积**；没有低对比度或颜色差异的豁免。
PNG 元数据、模型输出 JPEG 和编号不参与比较。

完全相同的解码像素沿用原路径。非完全相同时，所有以下规则必须同时成立：

| 检查 | 规则 |
| --- | --- |
| 图像与总面积 | 至少 100,000 像素；全部变化像素不超过原图的 1% |
| 形状 | 至多 4 个四邻接连通区域；每个区域必须符合下述细条候选 |
| 文字 | 重新 OCR；置信度至少 0.2 的文字原串与数量不变，每个框的四边偏移最多 2 像素；未截断成模型的 200 个元素后才比较 |
| 文字像素 | 任一变化区域与新旧 OCR 文字框（向外扩 1 像素）相交即拒绝 |
| 键盘 | 原有键盘启发式的有/无结果一致；键盘行文字或位置变化也由文字规则拒绝 |
| 敏感线索 | 输入仍检查原观察和新帧的敏感标签、候选文字与圆点；非输入容差也不接受新出现的敏感文字线索 |
| 目标 | CoreActions 两处从既有批准计划传入归一化 `point`；它不来自新一轮 OCR 重选。目标附近有独立保护，输入光标候选还需靠近此点 |

“滚动条候选”限于左右各 2% 边缘内、宽度至多 `max(3, width/200)`、高度
8 像素至半屏、不与目标保护区相交的竖条。“光标候选”需要新旧键盘线索都成立，
宽度至多 `max(2, width/240)`、高度 4 至 `max(12, height/12)`，至多一个。
两类都要求高至少为宽的四倍，变化像素占包围框至少 60%。

目标保护区是以批准点为中心、半径 `max(12, min(width,height)/40)` 的方框。
输入光标另受半宽 `max(24,width×0.12)`、半高 `max(12,height×0.05)` 的空间
邻域约束；非输入光标不能进入目标保护区。没有 target 的输入只能走完全相同
像素路径；没有 target 的非输入也不接受光标候选。所有常数都是本产品保守预算，
不是 Apple 对光标、滚动条或输入框的定义。

## 会通过什么、仍会拒绝什么

在文字、几何、目标和其他条件均稳定时，细窄滚动条淡出或一个光标闪烁可以
通过。不是任意 1% 变化都通过：小而紧凑的按钮变色、已识别金额或文字改变、
两处光标位置改变、整图轻微变色都会拒绝。时钟文字变动也可能保守拒绝。

没有屏蔽底部“键盘区”，没有猜测或排除 PiP 矩形。键盘重新出现时，只有已经
恢复同样布局且仅剩符合规则的小变化才可能通过；键盘正在过渡、换布局、消失
或 OCR 不能稳定复核时仍拒绝。没有新增自动重试或重复输入。

这些像素、OCR 和几何规则不能证明前台 App、真实焦点或字段身份。OCR 可能
漏认；一个未被 OCR 覆盖、恰好呈细条形的小变化可能与光标/滚动条候选无法
区分；只出现一次的新光标也不能证明焦点未转移。目标邻域只是额外拒绝条件。
逐次真实批准、敏感输入交接、原有后端/方向准入和结果不明不重放仍然必要。
不得把本匹配结果称为完整安全性、应用消费 ACK 或真实输入焦点证明。

## 资源和验证

RGBA 解码、全像素扫描、连通区域分析和容差路径 OCR 都在既有分析队列，
不在 MainActor 循环扫描。最多保留一份旧观察，按原 12,000,000 像素上限，
旧/新 RGBA 各最多 48,000,000 字节，变化掩码最多 12,000,000 字节；还存在
PNG、CGImage、OCR、栈和 JPEG 分配，**这不是总进程内存上限**。比较期间仍
受原实例的单次分析门约束；取消不会伪称已中断 Vision 的同步工作。

现有 `IOSPhoneScreenTests` 新增 12 个方法，用生产 PNG 解码与 revalidate，
覆盖细条正例、target 保护、全图淡色/等亮度反例、文字与几何改变、双光标、
键盘变化、第二/第三 OCR 候选敏感词、区域数量/面积和无效坐标；合成 OCR
只替代识别结果，没有复制另一个匹配器。既有 owner、时限、新帧与取消测试保留。

Apple 文档说明 [UIKit 与 Quartz 的默认坐标系不同](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/drawingwithquartz2d/dq_context/dq_context.html)。
新测试用上方光标/目标和下方键盘的非对称像素，检查现有 RGBA 解码行序与
top-left OCR/目标坐标的一致性。当前环境没有 Swift/Xcode，**34 个测试全部
authored / UNRUN**；没有声称已完成 Apple 编译、真实 PNG 方向/行序测试、
Vision、光标、键盘或真机输入验证。设备上仍需校准可用性和内存；若这些门
保守拒绝，应重新观察并由用户确认，不能自动扩大阈值或重放动作。
