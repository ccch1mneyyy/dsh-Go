# 图像与视频生成

> 2026-10-28。基于 0.9.7 的代码和 npm 包 `@deepseek-ai/dsh@0.2.1-rc.2`（只读）。本文写作时只做研究和设计；之后的决定和修订见 §8，冲突时以 §8 和 §4.6 为准。配合 [page-design.md](page-design.md)（骨架、间距）、[polish-guide.md](polish-guide.md)（对称、文案）、[settings-ia.md](settings-ia.md)（设置结构、＋ 面板）、[native-plugins-views.md](native-plugins-views.md)（工具卡）和 [plugin-seams.md](plugin-seams.md) 一起看。
>
> 标记：**〔源码〕** 是读过源码或仓库文档确认的；**〔推断〕** 是设计推断，没有实测；外部资料按附录 A 标 **V**（官方页面已抓取）/ **S**（只看到搜索摘要）/ **U**（未核实），抓取日期都是 2026-10-28。

**结论**：能接，而且大半基础设施已经在了。推荐把生成放在**主机**上：做一个 DSH 插件（暂名 `dsh-media`），API Key、调用、排队、计费都在插件里。它给模型三个工具（`generate_image`、`edit_image`、`generate_video`），也给人两个不经模型的斜杠命令（`/image`、`/video`）。App 不持有任何生成服务的 Key，只做原生的部分：生成模式和参数弹层、媒体卡、全屏查看、作品库、保存到相册。

这样选，理由有三条：

- **哪种主机都能跑完**。远程主机、中转主机、手机息屏，生成都在主机上继续。视频一跑就是几分钟，DSH 现成的后台任务（`ctx.jobs`）和「做完叫醒 Agent」正好接得住。
- **第一步零 App 改动就能用**。回复里写 `![](generated/cat.png)`，App 今天就会原生画出工作区里的图片，所有主机都行。插件先上，App 再逐步换成专门的媒体卡。
- **只写一份**。同一个插件在 DSH 网页版、dsh-TUI 里也能用。Agent 还能把生成的图接着用：放进网页、PPT，或者交给定时任务每天出一张。

App 侧真正缺的有四样：
1. 媒体卡：读工具结果里的 `dsh-go/media` 元数据。
2. 视频：播放器，以及保存视频（现在的 `MediaPlugin` 只收图片字节）。
3. 生成模式和参数弹层。
4. 作品库。

**反对它最有力的理由**：每台主机都得装插件，引擎也得在线。只想「画一张」的人走对话，还要多付一轮 DeepSeek 调用，多等 2–5 秒。对策有两条：本机运行时预装插件；生成模式走斜杠命令，不经模型。

实现分 9 步（M0–M8），可以逐步合入（§7）。插件、协议和待验证点（M0、M1、M7 的插件部分，R1–R6）在主机侧；媒体卡、视频、生成模式、设置、作品库在 App 侧。待定问题和后来的决定在 §8。

**小结**：DSH 没有「生成」这个概念，但积木是全的：
- 工具结果可以带图片块，也可以带展示元数据；
- 插件可以追加对话事件、跑后台任务、注册不经模型的命令；
- 密钥有只写的存储；
- 工作区文件在所有通道上都读得到。

App 能画工作区里的图片，不能播视频，也不能把视频存进相册。

## 2. 架构：生成在哪跑，Key 在谁手里

### 2.1 三个方案

| | a. DSH 插件 | b. App 直连 | c. 混合（App 直连图片，插件跑视频） |
|---|---|---|---|
| 生成在哪跑 | 当前主机（本机引擎或远程） | 手机上的 App 进程 | 图片在手机，视频在主机 |
| Key 在哪 | 主机的 `ctx.credentials`；App 只写不读 | 手机的安全存储 | 两边各一份 |
| 远程主机 | ✅ 结果直接落在主机工作区，Agent 能接着用 | ⚠️ 图在手机上；要给 Agent 用，得再传到主机 | ⚠️ 图片和视频在两个地方 |
| 手机离线、息屏 | 远程主机：照常跑完，回来就看到。本机引擎：断网就失败，插件按任务有效期续查 | ❌ 跟着 App 进程走；WorkManager 可以续查，但国产机常被掐 | 同 b / a |
| 几分钟的视频 | ✅ `ctx.jobs`：进度一行、可停止、完成后叫醒 Agent 或只更新卡片 | ⚠️ 要自己做排队、续查、通知 | ✅ |
| 成本控制 | 主机上一本账，所有入口（App、网页版、定时任务）共用一个额度 | 只管得住这台手机 | 两本账 |
| Agent 能不能用 | ✅ 工具就在 Agent 手里：先改写描述、再生成，用进网页和 PPT，定时生成 | ❌ Agent 看不到 | 只有视频 |
| 不经模型的「画一张」 | ✅ 斜杠命令（§1.1），不花 DeepSeek 的钱 | ✅ | ✅ |
| 网页版、dsh-TUI | ✅ 同一个插件（网页版先显示通用卡） | ❌ | 部分 |
| 实现 | 插件（Node）+ App 展示 | 适配器全用 Dart 写 + App 展示 + 后台调度 | 两套适配器 |
| 首次使用 | 本机预装；远程主机要装插件 | 填 Key 就能用 | 都要 |

### 2.2 推荐：a，并补上命令通道

**生成只在主机上跑，由一个插件负责。App 不碰生成服务的 Key。** 这就是方案 a，只是同一个插件开两个入口：对话里由 Agent 调工具；生成模式里，App 直接发不经模型的斜杠命令。这两个入口覆盖了 c 想要的「快、准、不花模型的钱」，又不用在手机上再写一套适配器。

```
App（生成模式 / 对话）
  ├─ 对话：「画一张…」 ─▶ session/prompt ─▶ Agent ─▶ 工具 generate_image / edit_image / generate_video
  └─ 生成模式：发送 ─────▶ commands/execute「/image …」+ 参考图 ─▶ 命令处理函数（不经模型）
                                         │
                              dsh-media 插件（主机）
                                ├─ 服务商适配器：OpenAI 兼容 · 方舟 · 百炼 · 可灵 …
                                ├─ 密钥：ctx.credentials（只写）
                                ├─ 账本：额度、用量、作品索引（主机上一个目录）
                                ├─ 图片：同步调用（≤ 3 分钟），文件写进工作区
                                └─ 视频：ctx.jobs（kind = media），按任务有效期续查，断点可恢复
                                         │
                 tool/result.meta["dsh-go/media"] · 事件 media/request、media/result · job/list 的 progress
                                         │
App：媒体卡（读工作区文件）· 全屏查看 · 作品库 · 保存到相册 · 完成通知
```

**为什么不选 b**：
- dsh-go 的身份是「Agent 的客户端」。把生成做成 App 里的一个孤岛，Agent 用不上，远程主机上的工作区也拿不到图。
- 手机进程管不住几分钟的视频任务：vivo 后台断网的问题已经踩过。
- 适配器要用 Dart 再写一遍，网页版和 TUI 又用不上。

**为什么不选 c**：同一件事两套实现、两本账、两份 Key。用户分不清这张图「在哪」。

**反对 a 最有力的理由**：
- 引擎和插件成了前提。本机引擎冷启动要几秒到十几秒。远程主机要先装插件。插件在 Node 里，是第二份代码。
- 对话入口每次多一轮 DeepSeek：多花钱，多等 2–5 秒。

**对策**：
- 本机运行时预装插件，没配 Key 前不注册工具（§7 M7）。
- 生成模式走命令，不经模型（§4.1）。
- 插件出现在插件市场，远程主机一键装。
- App 在当前主机没有这个插件时，生成入口显示「在此主机上安装」，不显示坏掉的按钮（〔推断〕：装插件走现有的插件市场流程）。

### 2.3 Key 的路径

| 环节 | 规定 |
|---|---|
| 填写 | 设置 › 能力 › 图像与视频 › 某个服务 › API Key。走插件设置的只写密钥字段（`settings/mutate`），App 画成「已配置 / 未配置」，复用 `SecretFieldTile` |
| 传输 | 本机引擎：进程内。SSH：SSH 隧道。中转：DSH Remote 的 Noise 端到端加密（`packages/dsh_remote/`）。**都不经过 dsh-go 自己的服务器**（我们也没有这样的服务器） |
| 存放 | 主机的 `ctx.credentials`。App 不落盘、不缓存、读不回来 |
| 绝不出现在 | 对话记录、工具参数、`presentationMeta`、命令参数、诊断包、分享链接、通知 |
| 服务商的结果地址 | 方舟、百炼、BFL 返回的是带签名的临时地址（10 分钟到 30 天不等，附录 A）。插件**拿到就下载**，记录里只写工作区路径，不写地址 |
| 复用模型渠道的 Key | 对 SiliconFlow、OpenAI、xAI 这类同时能聊天、能生图的服务，可以选「使用已有渠道」，不再填一遍。能否引用 `llm-pi-ai` 已存的凭据，要先验证（§7 R4） |

### 2.4 长任务、离线与后台

| 情形 | 行为 |
|---|---|
| 图片（多数 5–60 秒） | 在工具调用或命令里同步完成。插件给工具设 `timeoutMs: 180000`；服务商是异步接口的（BFL、可灵），插件在调用内部轮询 |
| 视频（1–5 分钟，附录 A） | 开一个 `ctx.jobs` 任务（`kind: media`），`label` 写「Seedance 2.0 · 5 秒」，`progress` 写「排队中」「生成中 · 42%」（服务商给了进度才写百分比）。工具立刻返回任务 id，卡片进入「生成中」 |
| 视频完成（对话入口） | 走 `tool-jobs` 默认的完成通知：叫醒 Agent，Agent 回一句话，这一轮结束时现有的「完成」通知照常弹出 |
| 视频完成（命令入口） | 插件自己 `wait` 这个任务，所以 `tool-jobs` 不会叫醒 Agent，也就不花模型的钱（`awaited`，§1.1）。插件追加 `media/result` 事件，卡片原地变成成片。App 另发一条「视频已生成」通知（§5.6） |
| 引擎重启 | 插件把未完成的远端任务（服务商、任务 id、提交时间）写进主机上的任务文件。重启后续查，直到服务商的任务有效期（百炼 24 小时、方舟 7 天，附录 A） |
| 手机离线（远程主机） | 主机照常跑。App 重连后读对话记录和 `job/list`，卡片自己更新 |
| 手机离线（本机引擎） | 没网就失败，卡片显示「网络不可用」+「重试」。已经提交的任务恢复网络后续查 |
| 停止 | 卡片上的「取消」走 `job/kill`，插件尽量调服务商的取消接口（多数服务商没有）。已经计费的照记账 |

**需要先验证**（§7 R2、R3）：
- 插件 `wait` 自己的任务后，完成通知是否真的不发；
- 对话空闲时由插件追加事件，App 的折叠和排序会不会出错。

### 2.5 插件和 App 之间的约定（v1；② 已作废，见 §8 的修订）

App 只认三样东西，全部随对话记录或 DSH 自带的 RPC 走，中转主机也有。不经桥接，所以不受 `hosts.md` 那张表的限制。

**① 工具结果的 `meta["dsh-go/media"]`**（`presentationMeta` 写入，≤ 8 KiB，不含字节）

```jsonc
{
  "v": 1,
  "rid": "m_7f3a9c",                 // 一次请求的 id；视频完成时靠它原地更新卡片
  "kind": "image",                   // image | video
  "status": "done",                  // running | done | failed（图片通常直接 done）
  "job": "media-1c2d",               // 视频：DSH 任务 id，App 用 job/list 看进度、job/kill 取消
  "items": [{
    "path": "/root/proj/generated/2026-10-28/cat-1.png",   // 主机上的绝对路径
    "mime": "image/png", "width": 2048, "height": 2048, "bytes": 3145728,
    "duration": 5.0, "poster": "…/clip-1.poster.jpg",       // 视频才有；poster 可缺
    "codec": "h264"                                          // 视频；App 用来判断能否原地播放
  }],
  "request": { "provider": "ark", "model": "doubao-seedream-5-0-pro", "label": "Seedream 5.0",
               "aspect": "1:1", "n": 2, "quality": "2k", "seconds": 5, "refs": 1 },
  "prompt": "画一只在窗台上打盹的橘猫",
  "revisedPrompt": "午后逆光，一只橘猫蜷在木窗台上打盹……",
  "cost": { "estimate": 0.6, "currency": "CNY" },
  "provenance": { "visibleMark": false, "c2pa": true, "implicitLabel": true },
  "error": { "code": "policy", "text": "描述未通过内容审核" }   // failed 时

```

**② 命令入口的对话事件**（插件 `session.append`，形状同上；已作废，见 §8 的修订）

| 事件 | 什么时候 | App 怎么画 |
|---|---|---|
| `media/request` | `/image`、`/video` 开始执行（命令注册时 `recordInput: false`，原始参数不重复写进记录） | 用户侧气泡：描述原文，下面一行小字「图像 · 1:1 · 2 张」，参考图缩略图 |
| `media/result` | 生成完成、失败或取消（同一个 `rid`） | 媒体卡；`command/done` 的 `sourceEventSeq` 指向它 |

**③ `job/list` 里 `kind: media` 的任务**：`progress` 一行字就是卡片上的进度文字，`status` 决定状态。

**工具的模型侧返回**只有文字：路径、尺寸、用时、改写后的描述。生成的图不进模型上下文，省掉图片输入费。模型要看，自己调 `read_image`。有一个可选的升级方向：把图以 `offloaded: true` 的图片块写进结果，这样能持久显示又不发给模型（§7 R1）。

**网页版与旧 App**：网页版不认 `dsh-go/media`，显示通用工具卡。插件的技能同时让模型在回复里写 `![](路径)`，所以网页版和没有媒体卡的旧 App 一样能看到图。新 App 看到媒体卡后，回复里指向同一路径的图片会去重，不画第二遍（〔推断〕：按路径去重，规则同产物卡）。

### 4.1 三个入口

| 入口 | 怎么触发 | 走哪 | 谁出描述 | 花费 | 适合 |

- 生成后不长篇描述画面，卡片会显示。

App 读目录的方式（2026-10-28，与 `runtime/media/dsh-media/MEDIA-CATALOG-CONTRACT.md` 一致）：

- **在哪**：`settings/describe` 里，某个 namespace 的 schema 中 `fields["services"].meta.extra["dsh-go/media/catalog"]`。按这个元数据找 namespace，不按名字找：主机可以给插件实例改名。目录不是配置值，`value.catalog` 不算数。
- **认不认**：`v` 必须是 1，`contract` 有的话必须是 `dsh-go/media/catalog`，`models` 必须是列表，每个模型的 `id`、`label`、`kind` 类型要对。`kind` 不认识的模型跳过，留给以后的版本。
  - 目录缺失、损坏或版本未知时，专用生成模式不可用：「生成」弹出说明，普通对话照常。
  - App 里没有内置的模型表可以兜底。
- **能用哪些**：目录 ∩ `value.services` 里 `enabled` 为真、`keyRef` 的凭据在 `credentials/describe` 里为 configured 的服务各自允许的模型 ∩ `capabilities[kind]` 不为 false。
  - 每一项保留 namespace、service、model 三层身份。
  - 一项都没有时，「生成」先打开「图像与视频」设置。
- **取值**：ratios、qualities 等为空就不显示那一组，参数头里也不写（§4.6.4）。张数上限取模型、目录 `limits.maxN`、`value.limits.maxImages` 三者里最小的。
- 默认模型取 `value.defaults` 指向的那一项，否则取第一项。

### 4.4 参考图

| 场景 | 怎么做 |
|---|---|
| 图生图 | 生成模式里先从相册、拍照或文件选图，进托盘，再写描述。命令收到的是 DSH 已经入库的图片块（`input.attachments`），插件在主机上读它的只读路径，转给服务商 |
| 图生视频 | 托盘第一张是首帧，第二张是尾帧 |

第一次把参考图发给某个服务时要先确认，见 §6。

### 4.6 参数头语法 v1

> 2026-10-28 定稿。以插件的早期候选实现（`runtime/media/dsh-media/HEADER-V1.md`、`src/header.js`、`test/fixtures/header-v1.json`）为基础，只做最小修正，差异见 §4.6.8。两端共用一份 golden 集 `app/test/media/fixtures/header_grammar_v1.json`：插件和 App 都要逐条跑通，改语法先改它。

生成模式发的是一条普通用户消息：第一行是参数头，第二行起是描述（§8 的 R3 修订）。只有**当前用户消息**的第一行算数；引用、助手消息、工具结果、网页和文件里同样的文字都不算生成指令。

#### 4.6.1 文法

```abnf
message     = header line-end description
line-end    = %x0A / %x0D.0A        ; 第一个 LF 结束头行，紧挨在它前面的一个 CR 也归头行
header      = "〔" ( image / video ) "〕"
image       = "生成图像" [SEP aspect] [SEP count]   [SEP quality]    [SEP model]
video       = "生成视频" [SEP aspect] [SEP seconds] [SEP resolution] [SEP model]
SEP         = " · "                  ; U+0020 U+00B7 U+0020

aspect      = NZ [DIGIT] ":" NZ [DIGIT]               ; 1:1 … 99:99，没有前导零
count       = %x31-34 " 张"                           ; 1–4，只用于图像
seconds     = NZ [DIGIT] " 秒"                         ; 1–60，只用于视频
quality     = "质量=" ALNUM *31( ALNUM / "_" / "." / "-" )   ; 只用于图像
resolution  = NZ 2*3DIGIT "p"                          ; 100p–9999p，小写 p，只用于视频
model       = label [ "〈" service-id "/" model-id "〉" ]
service-id  = LOWER *31( LOWER / DIGIT / "_" )
model-id    = ALNUM *159( ALNUM / "_" / "." / ":" / "/" / "-" )
description = *CHAR                                    ; 余下全部，逐字符原样

NZ = %x31-39   DIGIT = %x30-39   LOWER = %x61-7A   ALNUM = DIGIT / %x41-5A / LOWER
```

- 字段顺序固定，每个最多出现一次，都可以省。省掉的由主机用自己的默认值，解析器不补。
- 括号和中点：「〔」「〕」是 U+3014 / U+3015，「〈」「〉」是 U+3008 / U+3009，中点是 U+00B7。
- **label**：
  - 至少一个字符，UTF-8 不超过 160 字节，首尾不是空白；
  - 不含 `〔` `〕` `〈` `〉` `·`，也不含控制字符（U+0000–U+001F、U+007F–U+009F）；
  - 不以 `质量=` 开头；整体不能形如「数字:数字」，也不能是「数字 + 可选空白 + 张 / 秒 / p / k」（不分大小写）；
  - 还必须按 §4.6.3 的分类表落进「模型」那一行。`1.5p`、`-3:4` 这类 label 会先被当成清晰度、比例，然后报错。
- **空白**：就是 JavaScript `String.prototype.trim` 去掉的那组字符，即 U+0009–U+000D、U+0020、U+00A0、U+1680、U+2000–U+200A、U+2028、U+2029、U+202F、U+205F、U+3000、U+FEFF。Dart 的 `trim` 还会多去一个 U+0085，所以两端都按这张表自己判断，不调用语言自带的 trim。
- **长度**：头行（含括号，不含换行）UTF-8 不超过 1024 字节。描述 UTF-8 不超过 4096 字节，并且至少有一个非空白字符。
- 整条消息里不能有落单的 UTF-16 代理项。

#### 4.6.2 三种结果

| 结果 | 条件 | App | 插件 |
|---|---|---|---|
| 普通 | 不以 `〔生成图像` / `〔生成视频` 开头；或者紧跟类型词的那个字符不是 `〕`、`·`、空白，也不是文本结尾 | 原样显示 | 按普通对话处理 |
| 合法 | 是生成消息，并且完全符合 §4.6.1 | 隐藏参数头，气泡显示描述原文，下面加一行参数小字 | 按参数调用工具 |
| 非法 | 是生成消息，但不合文法 | 原样显示，不隐藏 | 说明是哪种错误，不调用付费工具 |

开头不能有空格、BOM 或引用符 `>`。下面几条都是普通消息：`〔生成图像的方法〕示例`、` 〔生成图像〕\n猫`、`> 〔生成图像〕\n猫`。`〔生成图像·1:1〕\n猫` 则是非法消息（`invalid_header`）。

#### 4.6.3 解析步骤与错误码

按下面的顺序检查，遇到第一处失败就给出错误码。这样两端对同一条输入总是给出同一个码。

1. 不是生成消息 → 普通（返回 null）。
2. 没有 LF → `missing_prompt`。第一个 LF 之前是头行（去掉末尾一个 CR），之后是描述。
3. 描述全是空白 → `missing_prompt`。
4. 头行超过 1024 字节，或描述超过 4096 字节 → `too_long`。先算头行；计算中遇到落单代理项 → `invalid_message`。
5. 头行不以 `〕` 结尾，或含 CR、LF → `invalid_header`。
6. 去掉首尾括号，按 ` · ` 切开。出现下列任一情况 → `invalid_header`：第一段不是类型词；超过 5 段；某段为空；某段首尾有空白；某段含 `〔`、`〕` 或 `·`。
7. 其余各段依次按下表分类。每段先做该类自己的检查，再做顺序检查：序号不大于上一段 → `invalid_order`。

| 段的形状（从上往下匹配） | 序号 | 合法条件 | 否则 |
|---|---|---|---|
| `±数[.数]:±数[.数]` | 1 | 是 `aspect` | `invalid_aspect` |
| `±数[.数]` + 可选空白 + `张` | 2 | 图像，且是 `count` | `invalid_count` |
| `±数[.数]` + 可选空白 + `秒` | 2 | 视频，且是 `seconds` | `invalid_seconds` |
| 以 `质量=` 开头 | 3 | 图像，且是 `quality` | `invalid_quality` |
| `±数[.数]` + `p` / `P` / `k` / `K` | 3 | 视频，且是 `resolution` | `invalid_quality` |
| 其他 | 4 | 是 `model` | `invalid_model` |

#### 4.6.4 生成

- 只写有值的字段，按文法顺序排列。头行和描述之间写一个 LF，描述原样接在后面。
- 写之前逐个字段校验。写完再解析一遍：类型、描述、各字段和模型身份都必须和输入完全相同，否则不发。
- App 的写法：
  - 图像总写张数。质量写目录里的原值并加上 `质量=`，比如 `质量=2k`、`质量=high`，不翻译成「高清」。
  - 视频按「比例 → 时长 → 清晰度 → 模型」的顺序写。
  - **音频 v1 没有定义，App 不发**，用模型的默认值；参数弹层也不放「声音」。
  - 目录里 ratios、qualities、durations、resolutions 为空时，对应字段不写，也不补 1:1、2k 这类默认值。目录里不合文法的值（比如视频清晰度 `4k`），App 不提供。
  - 质量的第一个选项是「自动」，选它就不写质量字段。
  - 模型总写成 `label〈serviceId/modelId〉`，label 照抄目录原文。

#### 4.6.5 模型身份与歧义

- **标记**：`〈serviceId/modelId〉` 指的是一个插件实例里的某个服务和某个模型。serviceId 是 `value.services[].id`，modelId 是目录里的 `models[].id`。
- **插件怎么认**：
  - 有标记：(serviceId, modelId) 必须是一个已启用、凭据已配置的服务允许的模型，label 也必须等于目录里的 label，否则拒绝。
  - 只有 label：在同类型的可用条目里**恰好有一个**同名，才用它。一个都没有或者不止一个，就拒绝并说明「模型不唯一」。不选第一个，也不按显示名去猜服务。
- **App 发出**：总带标记，哪怕 label 是唯一的。
- **App 读回**（编辑后重发、修改、↻）：
  - 有标记：按 (serviceId, modelId, 类型) 找。label 后来改过也认，再发时写目录当前的 label。
  - 只有 label：同类型里恰好一个同名才认。
  - 找不到或不唯一：模式里的模型显示「请选择」，选好之前发不出去。
  - 从卡片读回：工具结果 v1 的 `request` 里没有 serviceId，App 按 (provider, model id) 找。找不到唯一的一个时，↻ 退化成「修改」。
- **namespace**：v1 的头不带 namespace。App 持久化 namespace、serviceId、modelId、label 四项。同一个 (serviceId, modelId) 出现在不止一个目录 namespace 里时，App 不提供这些条目，因为头里区分不开。
- label 不合 §4.6.1 的条目，App 也不提供。

#### 4.6.6 显示与往返

- 只有**合法**消息才隐藏参数头。描述按原文显示，不 trim，也不改写。参数小字只读合法头里的值。
- 「编辑后重发」和卡片上的「修改」按同一套语法往返：参数头变回生成模式（模型按 §4.6.5 找回），描述放回输入框。当前主机用不了生成模式时，整条原文（连同参数头）原样留在输入框，照常可以发。
- **对话标题**：DSH 的默认标题取首条消息，把连续空白压成一个空格，再截断。App 只在两种情况下去掉参数头：
  1. 以 `〔生成图像` / `〔生成视频` 开头，后面是文本结尾、` ·`，或者 ` · …` 并且后面再没有 `〕`（标题在头里被截断）。这时显示「生成图像」或「生成视频」。
  2. 后面是 ` · …〕` 或 `〕`，从开头到第一个 `〕` 是合法头行，并且 `〕` 后面是文本结尾或一个空格。这时显示空格后面的部分；后面没有内容就显示「生成图像」或「生成视频」。
  - 其他情况一律原样显示，比如 `〔生成图像的方法〕示例`、`〔生成图像〕这个词是什么意思`。

```text

        （含候选 header-v1.json 全部样例，结果不变）

一、需要插件改的
1. 识别边界（src/header.js 的 parseGenerationMessage 开头）
   候选：只看 startsWith('〔生成图像' / '〔生成视频')。
         「〔生成图像的方法〕示例」报 missing_prompt，
         「〔生成图像的方法〕\n示例」报 invalid_header，
         普通的话被当成写坏的生成头。
   v1：  类型词后面紧跟的字符必须是 〕、·、空白（JS trim 那组）
         或文本结尾，否则返回 null，按普通消息处理。其余步骤不变。
   golden：plain 组里 kind-word-* 四条。
   同步：GENERATION_HEADER_INSTRUCTIONS 第一句改成
         「第一行以〔生成图像〕或〔生成图像 · 开头（视频同理）」。
2. 测试改读共享 golden（结构见 §4.6.7）
   header.test.js 逐组跑：valid（解析；canonical 的逐字节往返）、plain、
   invalid（错误码）、format（逐字节）、formatRejects（错误码）。
   titles 组只给 App 用，可以忽略。
3. 目录里的值必须能写进参数头
   ratios 合 aspect；qualities 合「质量=」后面的值；
   视频 resolutions 合 [1-9]\d{2,3}p；label 合 label 规则；
   model id 合标记规则。App 会丢掉不合的值和条目。
   M0 的 models.json 全部合规。

二、App 的约定（插件不用改，但要知道）
4. App 发出的头总带〈serviceId/modelId〉，哪怕 label 唯一；
   label 照抄目录原文。插件照候选校验：有标记时 label 也要等于目录 label。
5. 音频：v1 不定义，App 不发，视频用模型默认。
   要加的话放进 v2，两端和 golden 一起改。
   建议放在清晰度和模型之间，写成「声音=开」/「声音=关」。
6. namespace：v1 的头不带。(serviceId, modelId) 在多个 namespace 里重名时，
   App 不提供这些条目。多实例真要并存，v2 再把 namespace 放进标记。
7. App 读目录的方式
   只认 schema.fields.services.meta.extra["dsh-go/media/catalog"]；
   v 必须是 1；contract 有的话必须是 "dsh-go/media/catalog"。
   目录缺失、损坏、v 未知 → 专用生成模式不可用，普通对话照常。
   可选项 = 目录 ∩ value.services
            （enabled=true、id 合法、keyRef 的 credentials/describe 为 configured、
              models 里列出的目录 id、profile 一致）
            ∩ capabilities[kind] 不为 false。
   张数上限 = min(模型 maxN, 目录 limits.maxN, value.limits.maxImages)。
8. 空白和长度按规范列明的字符集和 UTF-8 字节计算。
   行为和候选 JS 一致，只是写明白了，Dart 端不依赖语言自带的 trim。

三、建议（不在 v1 里）
9. 工具结果 meta 的 request 里加 serviceId（作为追加字段，或者放进 v2）。
   现在 request 只有 provider + model。同一个 provider 下有两个服务配了同一个模型时，
   卡片上的 ↻ 认不出是哪个服务，只能退化成「修改」，让人重新选。
10. config.js 的 validateServices 只要有一个服务不合法（包括已停用的），
   runtimeSnapshot 就抛错，整个插件不注册工具。App 是逐个服务跳过的，
   所以会出现 App 提供了某个模型、插件却没有工具的情况。
   建议插件也逐个跳过，或者在设置页明确报出是哪一项错了。
```

### 5.5 成本与用量

| 位置 | 显示 | 来源 |
|---|---|---|
| 参数弹层 | 「约 ¥0.60」 | 目录单价 × 数量（或秒数） |
| 卡片元信息 | 「约 ¥0.30」 | 生成时的估算，写进 `cost` |
| 详情 | 「约 ¥0.30」；服务商返回了用量（OpenAI 的 token、方舟视频的 token）时显示「¥0.28」，不带「约」 | 同上 |
| 设置 › 图像与视频 › 用量 | 本月按服务汇总：张数、秒数、估算金额；每日上限 | 主机上的账本 |
| 不显示 | 服务商余额 | 大多数服务没有余额接口；只给「去控制台」的链接 |

**控制**（都在插件里执行，所有入口共用）：
- **每日上限**：按估算金额，默认值看 D6。超了就拒绝，卡片显示「今天的额度已用完」。
- **对话入口的视频**：每个对话第一次要走审批卡，可以选「本对话都允许」；图片在上限内不问。
- **数量和时长**：一次最多 4 张；视频时长取目录里的最小默认值。
- **不自动重试**：审核失败和余额问题都不重试。

### 5.6 完成通知

| 情形 | 通知 |
|---|---|
| 对话入口的图片 | 不单独通知；这一轮结束时现有的「完成」通知照常 |
| 对话入口的视频 | 被叫醒的那一轮结束时，现有的「完成」通知照常 |
| 命令入口，App 在前台、就在这个对话 | 不通知，卡片自己变 |
| 命令入口，App 在后台或在别的对话 | 新增一类「生成完成」：标题「视频已生成」或「图片已生成」，正文是对话标题，大图样式带封面。锁屏只显示「视频已生成」，同现有的脱敏规则。点开直达那张卡 |
| 设置 | 设置 › 通知 加一项「生成完成」，默认开 |

**能不能到**：和现有的完成通知一样。本机引擎有前台服务，App 一直连着。远程主机要 App 进程还活着、连接还在；进程被杀时没有通知，下次打开时卡片已经是成品。这一点不另做推送服务（§9）。

## 8. 决定与待定问题

> **已定（2026-10-28）**：
> - D1、D3、D5、D6、D7 按建议采用。
> - D2 **改为生成按钮提前**：生成模式（M5）和图片卡（M2）一起，作为第一个面向用户的版本上线。插件 M0、M1 照旧先做。
> - D4 按建议采用，另加「自动存到相册」开关，默认关。
> - D8 按建议显示估算费用，但只在价目可靠的服务上显示；拿不准时卡片上不显示，参数弹层和详情里照常显示。
>
> §2.5 的约定冻结为 **v1**：App 按它开发，插件按它实现。确实要改时追加 `v: 2` 并写明迁移，不能悄悄改字段。
>
> **修订（2026-10-28，依据插件侧的实测）**：DSH rc.2 不支持插件写自定义对话事件（R3），中转主机上的命令也有 60 秒时限，所以 §2.5 ② 的 `media/request` / `media/result` **作废**，生成模式不走命令通道。生成模式改为发一条普通用户消息，第一行是参数头，例如「〔生成图像 · 3:4 · 2 张 · Seedream 5.0〕」，第二行起是描述（语法见 §4.6）。插件的系统提示让模型按参数头直接调用工具；如果 rc.2 能指定本轮必须调用某个工具，就优先用它。App 隐藏参数头，用户气泡下面显示参数小字。工具结果仍是 v1 的 `meta["dsh-go/media"]`，所有主机都能用，结果也留在对话记录里。代价是多一次很便宜的模型调用。

|---|---|---|---|
| D1 | 生成放在**主机上的插件**里，App 不持有生成服务的 Key（§2） | 采用 | 每台主机都要装插件、引擎要在线。只想「画一张」的人走对话，会多一轮模型调用和几秒等待。命令通道和本机预装能缓解，但缓解不了「远程主机没装插件」的第一次 |
| D2 | 先上**对话入口**（M0–M2），生成模式放到 M5 | 采用：插件先上、零 App 改动，先验证有没有人用 | 大众用户找的是「生图按钮」，未必会想到直接说。生成模式晚上线，第一批体验就要靠「会说」。备选：M5 提到 M2 之后、视频之前 |
| D3 | 首发服务：**火山方舟 + 阿里云百炼 + OpenAI 兼容** | 采用：国内能用、人民币计费，兼容层顺带覆盖 SiliconFlow 和海外服务 | 可灵的视频口碑最好，却要等第二批。海外用户首选的 Gemini（Nano Banana）不在首发。OpenAI 兼容里的海外服务，国内用户多半要海外卡 |
| D4 | 作品文件放在**对话的工作区** `generated/`，主机另记索引 | 采用：Agent 能直接接着用，产物卡也认得出来 | 代码项目里会混进图片，git 状态变脏。本机引擎「重置运行环境」会把没存到相册的作品一起删掉。备选：主机统一目录 `~/.dsh/media/`，Agent 照样能读，作品库也更干净 |
| D5 | 「服务商水印」默认**跟服务商**（方舟默认开，百炼默认关）；App 内的「AI 生成」标注始终显示 | 采用：不替用户决定，也不把标识义务全压在 App 上 | 用户最烦水印，方舟默认在图上印「AI 生成」。全关画面最干净，但那样在国内分发时，标识就只剩 App 里那行字 |
| D6 | 花费护栏：**每日上限默认 ¥20**；对话入口的视频，每个对话第一次要审批 | 采用：防提示注入和手滑，能把损失兜在一天之内 | 多一道确认，和「产品不啰嗦」的取向冲突。上限会挡住正经大量出图的人，他们得先去改设置 |
| D7 | 本机运行时**预装**插件，没配服务时不注册工具 | 采用：本机用户零安装，生成入口一直在 | 运行时变大，插件的修复要跟着 App 发版。不用生成的人也背着它 |
| D8 | 卡片上显示**估算费用**「约 ¥0.30」 | 显示：花钱的功能，让人心里有数 | 价目一个月一变，还有汇率和档位，估算可能不准。显示错的钱比不显示更伤信任，界面也多一分账单感。备选：只在参数弹层和详情里显示 |

### 8.1 插件 0.2.0 实施记录（2026-10-31）

`@ccch1mneyyy/dsh-media`（原计划名 `@dsh-go/media`）已实现原生方舟、百炼、硅基流动图片与视频，保留 OpenAI 兼容图片，支持已核模型的单图编辑。目录仍为 `dsh-go/media/catalog` v1，结果仍为冻结的媒体 v1；无新命令、自定义事件或 App 改动。按 10-30 市场任务决定，**不预装**，由市场安装；已按用户授权使用备用组织；旧 `0.2.0` 被 staging 占用，改以 `0.2.1` 正常自动直发，npm 正式版本与公开下载哈希已核验，市场上线验收见 `market/VERIFICATION.md`。

视频采用 rc.4 的真实 `ctx.jobs`，完成后通过现有 tool-jobs 唤醒 Agent，再调用 `get_media_result` 输出终态媒体元数据。v1 取消以 failed/error.code=cancelled 表达；查询未确认取消时必须说明远端可能继续计费。方舟和百炼只支持排队取消，硅基流动无已核取消接口。

费用保护复用持久预算账本，默认本地每日 ¥20、未知价每次预留 ¥20，并逐次显式确认所有生成。当前无完整可靠价目，不显示假估价。**本地预留并非供应商真实账单的硬上限**，不应据 D6 原建议宣称可把全部损失兜在 ¥20。已提交或提交结果未知时不自动重发，也不释放预留冒充退款。审批显示参考文件的精确路径和目标端点，读取内容固定，文件替换后拒绝提交。

持久账本保存原请求、task ID 与输出日期。Host 重启后，原会话通过 `resume_media(rid)` 显式续查，绝不重复创建；费用已结算但原件尚未提交的窗口也可恢复。尚未实现自动扫描并重建全部 jobs；无 task ID 的不确定提交只能由用户核对服务商记录。恢复需要原服务配置身份保持一致。

验收为真实本地 HTTP mocks 与未改动的 DSH rc.4 headless CLI：图片和后台视频分别产生实际 Session/V4 日志、原件、预算审批与完成通知。headless 单次运行不等待普通 jobs，测试让第二轮本地模拟 LLM 响应保持打开直至 job 完成，不调用会抑制通知的 jobs.wait。未做真实付费调用或 Android/PRoot 验证。详细复现入口见 `runtime/media/dsh-media/VERIFICATION.md`。

## 9. 不做

- **App 直连服务商**（方案 b）、**一半直连一半插件**（方案 c）：理由见 §2.2。
- **我们自己托管、转售生成额度**：那样 dsh-go 就成了生成式 AI 服务提供者，要走备案、实名、审核，和 community.md「不托管用户内容」的定位相反。
- **蒙版涂抹式的局部重绘、图层、画布编辑**：编辑只做「用一句话改」。
- **Midjourney**（没有官方 API）、**OpenRouter 的聊天出图**（DSH 的模型适配器只收文字输出）。
- **App 内的成人内容开关**，以及任何放宽服务商审核的选项。
- **自建推送服务**来保证远程主机的完成通知：和现有的完成通知同等可达。
- **服务商回调**：手机和多数主机没有公网地址。
- **方舟组图（最多 15 张）、默认露出 4K 视频**：一次扣费太大。
- **跨主机合并的作品库**：作品库只看当前主机。
- **App 里剪视频、配乐、加字幕**。
