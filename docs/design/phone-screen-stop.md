# 手机操控：熄屏时的停止

2026-11-12。**未在真机上验证；本次新增回归未在本机运行**，下面的行为依据源码，验证交远端 CI 与真机。

## 问题

1.0.14 起，熄屏会把正在跑的对话取消（#848、#926、#968）。进程和引擎都活着，是 App 自己发的取消：

```
熄屏 / 无障碍服务离开
  └─ PhoneTaskSessions.stopAll        对每个任务项上报 stopped，空闲的占位项也算
       └─ Dart phoneStopWatcherProvider   看到 stopped 的上升沿
            └─ 取消本机引擎上所有在跑的对话
```

1.0.13 的原生代码只在有手机任务在跑时才停，改成按会话批量停止时没带过来。

## 现在的行为

### 空闲时不上报停止

`PhoneTaskSessions.stopAll` 仍然让之前的持有者和已排队的准入失效，但对空闲的记录不再建立停止保持，也不把会话写进 `stoppedSessions`。判断在 `PhoneTasks` 的同一把锁里做：

- 在跑、已暂停、或仍有调用在执行的任务：走原来的 `stopLocked`，停止消息、30 秒保持、会话围栏、技能取消和资源清理都不变。
- 冷启动的占位项、已结束的、已按空闲投影的任务：只推进纪元并结束过期的 scope。

用户主动停止（悬浮条、通知）不受影响，仍然可以停止冷的或空闲的记录。

### 停止时由原生记下有没有打断任务

状态推送（`PhoneControl.emitStatus`）是在 ticker 线程上重新取样，不是事件队列。任务刚开始或刚结束时，Dart 手里相邻的两份状态可能都对不上实际情况。所以这件事由原生在停止的那一刻判定：

- `PhoneTasks.stopLocked` 在结束任务**之前**、在锁内记下当时任务是否在跑，随 `Snapshot.toMap` 以 `task.interrupted`（布尔）上报。
- 「在跑」用的是对外投影的 active，和 `snapshot().active` 同一口径：已暂停或仍有调用在执行的任务即使超过空闲时长也算在跑，只有按空闲投影的不算。
- 停止保持期内再次停止，不会把已经记下的 true 冲掉。
- 保持到期、成功进入下一个任务、`clearStop`、有效的 `resumeForSnapshot`、成功的 `finishScope` 之后清零。

`interrupted` 只是记录事实，不参与准入、清理或恢复。

### Dart 一侧

`PhoneTaskStatus.interrupted` 是可空布尔：

| 原生上报 | 解析结果 | 停止沿上怎么判 |
|---|---|---|
| 没有这个字段（旧版原生） | null | 回退：上一份或这一份状态里 `task.active` 为真 |
| 布尔值 | 原值 | 直接用 |
| 有字段但不是布尔 | false | 不取消，不回退 |

`PhoneTasks.StopSource` 区分 `USER`、`SCREEN_OFF`、`ENVIRONMENT`，快照通过 `stopSource` 上报。两处熄屏入口（`PhoneControl.registerScreenOffNow`、`PhoneA11yService.screenOff`）明确传 `SCREEN_OFF`；关开关、服务离开走 `ENVIRONMENT`。有效的主动停止走 `USER`。

`phoneStopWatcherProvider` 里状态版本、launch 基线、`modernSeen` 的判断没有变。全对话取消仍只发生在没用过按会话隔离手机工具的旧路径上，且必须是 `USER`、确实打断了任务的停止沿；被动熄屏或服务离开不取消任何普通对话。没有 `stopSource` 的旧版原生保持兼容回退；有字段但为空、类型不对或未知来源不触发取消。

模型收到的通用停止消息只说明本轮手机操作中断、不重试旧动作，不假称用户主动停止，也不要求结束与手机无关的工作。现代会话仅由原生停止手机工具，不声称取消了主机推理。

无障碍服务先提交 typed 停止围栏，再中止驱动和撤销提示。`PhonePrompts` 对带撤销原因的 `STOPPED` 复用已有 worker 中断出口；只有没有撤销原因的真实用户停止选择才转成 `Decision.STOP` / `HandoffResult.STOP`，避免锁屏 ticker 或 UI 关闭抢先伪造 `USER`。

## 没有改变的

1. **准入围栏。** 每次 `stopAll` 仍对所有既有记录推进 `admissionEpoch`，旧的排队调用等到保持期之后也会被拒绝。
2. **持有者围栏。** 空闲分支推进 `lifecycle`；内部在跑但已按空闲投影的任务会走 `endLocked`，清掉原任务的批准、免确认、可视化授权和插话。
3. **批量提交的顺序。** 持锁时提交全部记录，再在锁外取消驱动和问答、发布快照、清理。
4. **重复通知不延长旧保持。** 第二次熄屏广播只让旧票据失效，保留第一次的 `stoppedUntil` 和原因，不产生新的上升沿。
5. **物理资源不提前释放。** `pending`、`running`、`cancelling`、`closing`、清理失败、日志和技能 scope 的结算门槛都不变。

## 已知的局限

- **状态通道不是事件队列。** 整个停止保持期都没被取样到，或者取样前已经被显式恢复，Dart 仍然看不到停止沿。`interrupted` 只解决「已经看到停止沿时，怎么判断有没有打断任务」。
- 退休记录里冻结的快照是历史，不能拿它的 `interrupted` 决定现在要不要取消。

## 解锁后只开放新一轮

不增加亮屏/解锁广播，也不自动续作。在现代调用的 `admit` 入口、registry 锁外重新读取实际 `isEnabled() && !isLocked()`，读取前记录 registry `epoch`；锁内要求它仍匹配，再检查来源和旧记录结算。`stopAll` 与 `retire` 都推进这个既有纪元，读取期间新发生的熄屏不能被旧的「已解锁」结果撤销。动作发送处已有锁屏、开关与所有者守卫，状态取样不代替动作许可。

- `screenStoppedSessions` 只由第一次仅熄屏的会话围栏建立；有效主动停止、任何非熄屏的 `stopAll`、显式恢复与 `retire` 会撤销资格。非熄屏停止后再次收到熄屏广播不会降级来源，即使 30 秒保持已过或旧 run 已结束。
- 新调用必须是此前没有原生记录、也没有真实 host run-end 的新 `runId`。旧记录的 `pending`、`running`、`cancelling`、`closing`、`ending` 必须排空；物理资源确认释放，清理没有失败，journal 与技能 scope 已结算；已经收到的 end 必须完成结算。缺少确认时明确拒绝；清理/存储恢复后可由新调用重新检查，不在准入处自动重试资源清理。
- 只移除会话级围栏，不调用 `resume`、不清旧 `Task.stopped`、`admissionEpoch` 或 `endedRuns`；同会话熄屏前已有的冷/排队记录也保持为旧 run，不能借新轮放行复活。旧所有者、批准、免确认与原动作不继承。30 秒不是旧 run 的围栏期限。
- 不要求尚未到达的 host end：停止后本机资源确已排空即可接纳新 run。支持先 end 再新 run，也支持新 run 已开始后迟到的旧 end；旧 end 只结算原记录。
- 旧悬浮条按钮必须仍匹配 active owner；已经失效的旧按钮不算新的有效用户停止，不能借它停止后继。`retire` 清掉本次 launch 的恢复资格，新引擎不自动接回旧任务。

## 无障碍服务的熄屏广播

`PhoneA11yService` 的熄屏广播在手机操控总开关关着时仍然生效，这里没有改。这个服务还承载桌宠和截屏的入口，`stopAll` 会先提交停止围栏，再中止驱动、结束悬浮问答；总开关刚关上不代表之前的系统操作和提示已经排空，丢掉这条清理路径会留下新的空档。这条广播明确归为 `SCREEN_OFF`，即使打断了手机任务也不通过 legacy 监听取消普通对话。

## 真机上要看的

记下机型、Android 版本、ABI。

1. 只有普通对话在跑、没有手机任务：熄屏，对话应继续。分别在手机操控开和关（无障碍服务仍连着）下各做一遍，连续熄屏解锁三次。
2. 本次引擎启动后用过一次手机工具，再重复第 1 步。
3. 手机任务正在操作主屏或后台屏时熄屏：任务应停止，旧动作不重试，资源在实际清理后释放。
4. 手机任务进行中在悬浮条上点停止：手机操作停止；现代路径不声称取消主机推理，legacy-only 保留原来的取消行为。
5. 手机任务刚开始就熄屏：手机任务停止，普通对话继续；结束后立刻熄屏也不应取消普通对话。
6. 解锁后发起新一轮手机任务应可用；旧一轮重试、旧批准和免确认不得复活。分别覆盖有锁屏与无锁屏设备。
7. 先手动停止再熄屏，或熄屏后关开关/服务离开再解锁：不应因此恢复。
8. 清理尚未排空或失败时新轮应拒绝；明确完成原资源清理后新轮可用，不重放旧动作。
