# 发布临时文件的持久归属与重启清理（M3-1b）

## 结论及适用边界

M3-1 的同目录临时文件 + `renameat2(RENAME_NOREPLACE)` 负责最终名称的原子提交；本文补上临时资源的持久登记与下一次 App 启动清理。所有产品操作仍在一个 App、一个主 Node 引擎的边界内。Linux 实测通过不代表 OpenHarmony 真机、ArkTS 宿主或目标文件系统已经验证。

发布时先持久登记再 `open('wx')`，打开后记录设备号、inode，并向该文件写入随机归属标记。标记 fsync 与 identified 账本提交都成功后，才开始第一段内容复制。成功提交或失败删除临时文件后才注销登记。下一次主引擎启动，先获得真实内核排他锁，再恢复旧 owner 的记录，最后公布发布服务。

只凭设备号 + inode 不足以跨进程证明归属：已经用真实中途 SIGKILL、删除旧临时文件并创建替代文件的实验复现 inode 被复用。旧候选会删除替代文件。当前实现追加文件自身的 `user.dsh_go_ownership` xattr，值为该条记录的随机 UUID；新 inode 不会自然继承旧文件的标记。恢复要求路径、设备号、inode、标记全部吻合，同时持有已验证文件句柄直到检查和 unlink 完成。原反例及修正后的复核证据随交付包保存。

这是私有应用目录内、遵守同一协议的写入者之间的协议。它不防能任意改写账本或伪造 xattr 的同权限恶意代码。同步 lstat + unlink 也不是操作系统提供的原子 compare-inode-and-unlink；任意外部原生写入者不在已证明的竞争模型内。

## 文件、身份和互斥

- 宿主必须在启动前提供显式、已存在、绝对且非根目录的 `DSH_HOME`。主引擎规范化该目录，在其中使用 `ohos-ownership/`；不回退到 cwd。
- 账本目录必须是真实目录且对组及其他用户无权限（0700）；符号链接或宽权限目录被拒绝。
- `.lock` 是固定锁文件，0600、不得为符号链接。`lockExclusive(fd)` 使用 `flock(LOCK_EX|LOCK_NB)`。第二个持有者明确报 busy；本进程关闭句柄或死亡后由内核释放。锁文件绝不删除或替换，否则旧、新 inode 的锁可能同时被持有。
- `ledger.json` 是 schema 2 的完整快照；每条记录含 token、ownerId、本次 pid、临时路径、发布目标和状态。pid 仅用于诊断，ownerId 是每次主引擎初始化新生成的 UUID，不依赖 pid 不重用。
- `ledger.pending` 是协议保留的固定提交槽。启动取得锁且成功解码已提交账本后，只清理这个精确槽位；它不是对发布临时文件的前缀扫描。损坏的已提交账本使启动失败，并保留 pending 作为证据。pending 若为符号链接等非普通文件也拒绝处理。
- 账本目录本身、其内部文件及通过父目录符号链接解析进去的路径，不能被登记成临时资源或发布目标。

账本提交顺序：独占创建 pending → 写完整 JSON → fsync pending → 关闭 → rename 覆盖 ledger.json → fsync 账本目录。只有全部成功后，内存视图才接受新状态。持久化失败使实例进入 poisoned 状态，后续新操作明确拒绝；不能在不知道提交是否完成时继续用旧内存状态写账本。关闭等待已经排队的操作，拒绝新操作，然后关闭目录及固定锁句柄。

本轮验证范围是进程 SIGKILL 与注入的文件操作失败。新建账本目录的父目录 fsync，以及发布目录中最终 rename / 清理 unlink 的目录持久性，尚未构成整机突然掉电的完整证明。不得把本轮结论写成“任意断电后都不丢状态”。

## 发布状态与恢复规则

| 状态 | 已完成的事实 | 本次正常收尾 | 后续进程的恢复 |
| --- | --- | --- | --- |
| reserved，临时路径尚未创建 | 登记已持久写入 | 可撤销未创建的登记 | 路径不存在则注销 |
| reserved，路径已存在 | 创建与持久身份确认之间可能中断，也可能是 wx 冲突的外来文件 | 只有本次仍持有创建句柄和可信身份时才做本次清理；wx 失败可仅撤销意图 | 不推断归属；保留文件和记录，报告 unresolved |
| identified | 设备号/inode 与创建标记已确认，标记 fsync 及账本提交已成功 | 复制、fsync、原子提交；或在句柄仍打开时删除自己的临时名称；关闭后注销 | 仅旧 owner、身份和标记吻合时删除精确路径；任何不符均保留 |
| identified，但路径已消失 | 可能已经发布或已经删除，只是注销未完成 | 注销 | 只注销旧记录，绝不按 finalPath 去删除目标 |

恢复忽略当前 owner 的条目；不枚举目录、不从 `.dsh-ohos-publish-` 前缀推断归属。最终目标仅记录作为发布关联信息，从不成为清理对象。已识别条目仍有同名路径时拒绝注销，防止在物理清理未完成时丢失追踪。

创建后、identified 持久提交前的狭窄窗口有意保留为 unresolved。文件系统没有把“创建文件”和“修改另一个账本”合为一笔事务的接口，本轮没有发明这个保证。真实六阶段强杀测试包含该窗口；该测试通过的含义是安全保留及告警，而不是声称它已经自动回收。主要验收的“写入到一半被杀”发生在 identified 之后，已验证自动清理并再发布成功。

## 原生扩展与文件系统失败

宿主 linked NAPI 模块新增三个同步入口，原来的 `renameNoReplace` 保持原语义：

- `lockExclusive(fd)`：真实非阻塞 flock。已有持有者的 EAGAIN / EWOULDBLOCK 转为账本 busy；其余错误保留。
- `setOwnershipMarker(fd, token)`：`fsetxattr(..., "user.dsh_go_ownership", token, XATTR_CREATE)`。只能创建，不覆盖已有标记。
- `getOwnershipMarker(fd)`：读取同一属性。仅 ENODATA 表示没有标记，返回 undefined；ENOTSUP、ERANGE、权限等错误继续抛出。

不支持 xattr 时，不退回到存在已知误删反例的 inode-only 规则。identify 失败发生在第一段复制之前，本次若还能证明创建归属则正常清理；若进程此时死亡，重启只能保留 reserved 未决条目。缺失原生入口、缺失应用目录或账本损坏都阻止服务安装。恢复时标记读取失败保留该文件与条目，并报告 unresolved。

这些函数未增加第三方依赖。实际 Linux `.so` 用于在 Node 启动前注册 linked module 的测量夹具；它不是 OpenHarmony 产品二进制。OpenHarmony 产品源码仍需随宿主交叉编译、签名并在应用数据目录验证。

## 与 O4b 的共用边界

`openOwnershipLedger` 与附件 provider 无关，只接受路径、目标及创建后的身份；atomic publisher 通过 reserve / identify / release 接入。后续 O4b 可由同一主引擎持有账本，为每个 git worker 的确切临时资源登记 token，并由主引擎在收到 worker 退出后收尾。

O4b 尚未接完，不能把“API 可复用”说成“git 硬取消已经修好”。接入必须覆盖 git 适配器实际产生的全部临时元数据 I/O，不能只登记最外层 index，也不能收到退出后按前缀扫描。worker 必须在创建前请求主引擎持久 reserve，创建后请求/完成同样的 marker + identified 屏障，第一段写入在屏障之后；失败或硬终止由主引擎按确切 token 处理。应新增限定单个 worker owner/task 的回收入口或明确的主引擎资源表，但不能直接调用“回收所有旧进程条目”去清理仍在运行的兄弟任务。该扩展应单独出补丁与硬取消实测。

## 可复现验证与真机清单

账本单元边界测试必须加载真实 linked module，包含：持久登记/标记、current owner 保留、真实 flock 排他、八路交错串行化、替换文件保留、内部路径与别名拒绝、损坏账本/pending 保留、write/sync/rename/目录 sync 四类提交失败、标记同步失败及不支持时保留、已提交但未注销恢复、关闭等待在途持久化。故障注入只替换本次 ledger 实例的 fs 接口，不改全局 Node 模块；它证明给定失败返回下的行为，不冒充设备上实际发生过 EIO。

更高层以生产 preload + 实际 attachment/session provider 执行六个屏障位置的真实 SIGKILL 与新进程启动。旧版先失败，新版再通过；重启时读取磁盘账本而非父进程转交归属。复核代理独立重复正常路径和 inode 替换反例，并按冻结 SHA256 给出结论。完整 O0 同剧本随后执行，失败点表保留最初 home 前置条件缺失的失败及修复测量驱动后的结果。

真机尚待核实：

1. App 私有数据目录权限及 `DSH_HOME` 的启动顺序；第二主引擎确实不能启动。
2. fsetxattr/fgetxattr 所需 syscall 的 seccomp/SELinux 与文件系统支持；标记跨 App 杀进程/重启保留。
3. flock 的内核支持、杀进程释放与固定锁 inode 不被宿主清理。
4. fsync 普通文件和账本目录的支持；错误是否原样可见。
5. renameat2(RENAME_NOREPLACE) 正常成功、目标已存在、EINVAL 分支；回退仍可能留下部分最终文件。
6. 真机写入到一半杀 App → 重启自动清理 → 再发布成功；保留无关同前缀文件及已替换文件。
7. 后续若要求整机突然掉电保证，单独补齐目录持久性与掉电测试，不以 Linux SIGKILL 替代。
