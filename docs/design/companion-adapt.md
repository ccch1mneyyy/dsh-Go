# 伙伴小屋：让用户自己的 AI 适配模型

2026-11-08 起草。起因：有用户导入「大肥鱼 4096」时出了蒙版问题。用户希望兼容问题交给用户自己的模型去解决，体验上用户感觉不到。

## 0. 结论

- **适配分两层。**
  - 确定性的兼容由 App 自己处理，不用 AI：渲染、文件结构、蒙版、贴图尺寸、未登记的动作表情。这部分已经做了一批，见 §2.2。
  - 需要判断的适配交给用户自己的模型，比如：这个参数是不是转头，哪个表情算害羞，点哪里算摸头，哪些参数是换衣服。
- **AI 只产出数据，不写代码。** 它输出一份适配表（adapter，并进 character.json，见 §3）。App 负责执行和验收：套上适配表，自动检查；不对就把检查结果发回给 AI 再改，最多 3 轮。舞台脚本永远是我们发布的那份。
- **用户无感。**
  - 导入时 App 自动体检，几秒钟。
  - 需要 AI 时，界面显示「她在适应新身体…」。
  - 结束后用一句话说明结果。
  - 第一次用 AI 适配时说明会发什么给模型：参数名单和几张小截图，不发模型文件。之后默认自动进行。
- **「导入前让 AI 查一下能不能适配」不需要 AI。** 「能不能用」由体检确定性地回答；AI 只负责「怎么用得好」。
- **适配表按模型指纹保存。** 指纹是 moc3 的 sha256。以后可以上传到宠物/伙伴市场：下一个导入同一模型的人直接复用，不花 token。

## 1. 现在哪些地方依赖「标准模型」

stage.js 的程序化动作直接写死了这些 Cubism 标准参数名：

- `ParamAngleX/Y/Z`、`ParamBodyAngleX/Y/Z`、`ParamBreath`
- `ParamEyeLOpen/ROpen`、`ParamEyeBallX/Y`、`ParamEyeSmile`
- `ParamMouthOpenY`、`ParamMouthForm`
- `ParamBrowLY/RY`、`ParamBrowLAngle/RAngle`

character.json 里还有这些，默认值都是按鲸娘调的：

- 触摸区 `zones`：按画面高度比例切出头、脸、身体、尾巴。
- 取景 `framing`。
- 情绪表 `emotions` 和动作表 `actions`。
- 尾巴参数 `tail`、初始姿势 `pose`。
- 名字。

两类模型的现状：

- **大肥鱼这类按标准命名的模型**（509 个参数，头部用标准名，另有服装开关 `Clothes1–5`、表情开关 `key1–13`、动作开关 `Movement1–3`）：转头、眨眼大多能用。但情绪、触摸区、尾巴、换装都不认识。
- **命名不标准的模型**（Cubism 2 时代的 `PARAM_ANGLE_X`，或作者自己起的 ID）：连转头、眨眼都没有。

AI 要补的就是这些。

## 2. 流程

```
导入 ─► ① 体检（App，1–3 秒）─► ② 规则修复（App）─► ③ AI 适配（只在需要时）─► ④ 验收（App）─► ⑤ 保存 / 分享
                      │                                        ▲                     │
                      └─ 用不了：一句话说明原因                 └──── 不对就带着检查结果再来，最多 3 轮
```

### 2.1 体检（probe）

stage.js 加一个 `?probe=1` 模式：只加载模型，不进入陪伴逻辑，在后台 WebView 里跑完，输出 `probe.json`。内容：

- **能否运行**：能不能加载、moc3 版本是否受 Core 6 支持、加载用时。
- **成本**：图元数、蒙版组合数（大肥鱼是 49）、贴图尺寸和估计显存、测试渲染的帧率。
- **参数表**：每个参数的 id、cdi3 里的显示名、所属组、最小/最大/默认值；另有部件表。
- **素材**：表情、动作（包括没登记的文件）、物理、HitAreas、EyeBlink/LipSync 组。
- **标准参数覆盖**：§1 列的 18 个参数，模型里有几个。
- **缩略图**，总数控制在 20 张以内：
  - 默认姿态一张。
  - 候选参数推到两端各一张，只挑「像转头、眨眼、张嘴」的候选。
  - 每个表情一张。

结论分三档，导入页用一句话给出：

- 能直接用。
- 能用但需要适配。
- 用不了，例如 Core 不支持、文件损坏。

### 2.2 规则修复

已做（8da76ad2）：

- 蒙版超过 36 种时多给贴图，再多就用高精度蒙版。
- 蒙版分辨率提到 1024。
- 贴图按设备上限缩小。
- 自动发现 model3.json 没登记的 `.exp3/.motion3`。
- 模型文件夹直接打成 zip 也能导入。
- 高分屏关掉 MSAA；帧率跟不上时自动降分辨率。

要补：

- Cubism 2 风格的 ID 有固定对照（`PARAM_ANGLE_X` → `ParamAngleX`，`PARAM_EYE_L_OPEN` → `ParamEyeLOpen`…），直接按表映射，不用 AI。
- 模型有 HitAreas 时，直接生成触摸区。
- EyeBlink/LipSync 组里的参数，直接当作眨眼和口型。

### 2.3 AI 适配

**触发条件**：没有 character.json，或者规则修复后仍有缺口：标准参数覆盖不足、没有情绪表、触摸区还是默认值。

**发给模型的**：

- 任务说明、适配表的 JSON Schema、我们的参数词表（每个语义参数的含义、范围、正负方向）。
- probe 的精简版：参数 id、显示名、范围（几百个参数按组压缩），以及表情名、动作名、部件名。
- 缩略图：只在模型能看图时发。
- **不发** moc3 和贴图原文件。

**收回的**：一份 adapter JSON（§3）。只能引用 probe 里出现过的 id，数值会被夹到参数范围内。

**两种模式，同一份契约**：

- **轻量模式**：App 直接调用户配好的模型（伙伴的 light client），要求只输出 JSON。
- **完整模式**：交给 host 上的 agent，做成内置 skill `companion-adapt`。输入输出契约相同，agent 可以多想几步、自己核对。渲染和验收仍然由 App 做，因为 agent 那边没有舞台。

**用哪个模型**：用户当前用的那个。没配 key 时跳过这一步，只用规则修复的结果，并提示用户：「配好模型以后，可以让她再适应一下」。

### 2.4 验收

App 套上 adapter 后，在后台做三层检查：

1. **结构检查**：id 都存在，数值在范围内，没有把开关类参数（换装、水印）当成表情。
2. **动作检查**：按 adapter 分别驱动「向左看」「眨眼」「张嘴」「开心」各一下并截图，和默认姿态比像素差。没有变化说明映射错了；变化落在画面外说明方向或幅度错了。
3. **看图检查**（模型能看图时）：把截图连同「这张应该是什么」发回去，让模型指出哪张不对，再改 adapter。

最多 3 轮，最后用得分最好的那一版。界面上显示她在「试衣服」。

### 2.5 保存、修正、分享

- adapter 写进 character.json，带上 moc3 指纹。
- 菜单里「她的设定」旁边加两项：
  - 「重新适配」。
  - 「这里不对」：比如用户说「摸头没反应」「开心的时候脸是黑的」。这句话作为下一轮 AI 适配的额外输入，AI 改表，App 验收。所谓「即时的兼容 skill」就是这样：用户说一句话，几秒后生效。
- 有市场以后，adapter 和模型分开存。模型本体有版权问题，adapter 只是参数 id 和数值。导入时先按指纹查市场有没有现成的适配表。

## 3. 原设计的适配表（市场合同；当前 App 格式见 §6.1）

这里的单目标 `params`、无横坐标 `zones`、`toggles` 等字段是 C720 市场合同的格式，不能直接当作当前 App 的执行合同。当前 App 的实际格式、两种模式共用请求、白名单和证据边界见 [适配契约与接线](companion-adapt-contract.md)。

```json
{
  "adapter": 1,
  "moc": "<moc3 的 sha256>",
  "params": {
    "ParamAngleX": { "id": "PARAM_ANGLE_X" },
    "ParamEyeLOpen": { "id": "EyeL", "scale": -1, "offset": 1 },
    "ParamMouthOpenY": { "id": "MouthOpen", "scale": 0.8 }
  },
  "emotions": { "shy": { "expression": "脸红", "face": { "ParamEyeSmile": 0.4 } } },
  "actions": { "wave": { "motion": "挥手" } },
  "zones": [{ "id": "head", "from": 0.02, "to": 0.19 }],
  "framing": { "zoom": 0.86, "y": 0.06 },
  "tail": ["Param_Angle_Rotation84"],
  "toggles": { "outfits": [["Clothes1"], ["Clothes2", "Clothes3"]], "hide": ["Paramshuiyin7"] },
  "notes": "给用户看的一句话：比如「她没有尾巴参数，摇尾巴用摇身体代替了」"
}
```

- 舞台的实际仿射语义：`set(v)` 使用 `v*scale+offset`；`add(delta)` 只将 `delta*scale` 加到当前 native 值，不再次加 offset。最后由模型按 native 范围限幅。
- `toggles` 是市场数据字段，本期 App 的 AI 适配不执行它，也不自动设定服装、水印、署名或显隐。

## 4. 安全、隐私、成本

- **AI 的输出只当数据**：先过 schema，id 走白名单（只能是 probe 里有的），数值夹紧，未知字段丢弃。不执行任何代码，也不改舞台脚本。
- **发出去的只有参数名单和缩略图。** 第一次适配时说明一次，设置里可以关掉「让 AI 帮忙适配」。
- **成本**：500 个参数压缩后约 6–10k token，一轮输出 1–2k；看图按模型计费。导入时提示「会用你的模型一次」。

## 5. 分工

- **前端（我）**：
  - probe 模式。
  - §2.2 要补的规则。
  - adapter 在舞台上的执行。
  - 验收用的截图和像素检查。
  - 导入页的体检结论、「重新适配」和「这里不对」的界面。
- **后端（GPT Pro）**：
  - adapter 的 JSON Schema 和参数词表定稿。
  - 轻量模式的提示词、完整模式的 `companion-adapt` skill。
  - 评测集：收 20–30 个公开可用的模型，标准命名、Cubism 2 风格、自定义命名、高精度多蒙版各几种；量适配准确率、轮数和 token。
  - Core 6 不支持的 moc 版本清单。
  - 市场里 adapter 的存储和按指纹查询，并入 C700。
- **授权**：adapter 能不能公开分享，并入 C730 一起核实。

## 6. 分期

1. **第一期（2026-11-08 已做）**：probe、§2.2 的规则补完、舞台的 `params` 别名、轻量模式一轮纯文本适配、结构检查。实际落地和上文的出入：
   - **体检**：没有单开 `?probe=1` 模式，舞台加载完就在 `ready` 消息里附上体检报告（`stage.js` 的 `probeReport`）。大肥鱼 509 个参数的报告约 43 KB。
   - **规则**：参数名比较时忽略大小写和下划线，所以 `PARAM_ANGLE_X` 自动对上 `ParamAngleX`；另有同义名表。范围差十倍以上才自动缩放，±30 对 ±10 这种不缩放，以免自带的鲸娘也跟着变样。
   - **适配表**：单独存成 `character/adapter.json`，不改 character.json。舞台的 `adapter` 命令实时套用，删掉文件就恢复原样。适配表里的 `actions` 可以把她的手势换成模型自己的动作。
   - **触发**：判断逻辑在 `companion_adapt.dart` 的 `companionAdaptWanted`，规则是缺核心参数、触摸区只能用默认值、没有情绪表、有尾巴参数却没登记，满足任一条就触发。每个模型（按 moc3 指纹）只自动试一次；菜单「适配这个模型」可以带一句「哪里不对」重来，也可以撤销（撤销后不会再自动适配回来），还有一个开关控制「导入新模型时自动适配」。
   - **第一次先问**：用户还没同意过时，自动适配不直接发请求，而是在输入条上方出一张小卡片，说明会发什么、会用一次 Key，按「适配」才发；「不用了」就这个模型不再问。答应过一次（或从菜单手动适配过一次）以后才真正自动。菜单里的说明列全了发出去的内容：模型名、参数名单、表情动作和部件的名字、用户写的话和现在的适配表。
   - **校验补充（#753 审查）**：表情的 `face` 是叠加量，按参数自己的范围夹（转头可到 ±30），不再一律夹到 ±1；夹完变空的触摸区丢掉；适配表可以带 `framing`（zoom 0.3–3、y ±1）；`pose` 直接写模型参数，不经过别名；适配表里的 `moc` 指纹和当前模型对不上时整份不用。
   - **报错**：Cubism 2 的旧模型（.moc）和 moc 版本太新的模型，各自给出明确原因，不再只显示「加载失败」。
   - **还没做**：截图验收和看图多轮（第二期），完整模式的 skill（第二期，交给 Pro）。也还没用真实的模型接口跑过：本机没有 Key，测试里的模型回答都是模拟的。
2. **第二期**：截图验收、看图多轮、「这里不对」反馈、完整模式 skill。
3. **第三期**：adapter 进市场，按指纹复用。

### 6.1 C906（承接 C810）：两种模式共用的本地执行契约

纯函数在 `companion_adapt_contract.dart`，原 `companion_adapt.dart` 继续导出同一 API。请求改为有版本的 JSON 数据包；全部 800 个可用参数位置、已知映射与未知覆盖、既有触摸几何、裁剪状态分别表达。完整模式使用随包的 `companion-adapt` 技能，读取与轻量模式逐字相同的 system 提示。

完整替换从 `ruleAlias` 重建映射，再叠加本次合法候选 params。C906 的 probe 报告完整规则及原始仿射系数，保留很小的参数范围；checker 按替换后的有效表判断 face。当前 `linked` 可能来自即将删除的旧 adapter，不能作替换后依据，也不能据它猜 scale=1。旧报告的规则未知时仅接受显式合法映射支持的 face；判空保留旧表，current 只是参考而不自动合并。

本期 probe 只有加载成功的表情/动作名字，没有已检查的效果和副作用。新的 AI 候选必须另由 App 提供 `CompanionAdaptEvidence`，没有证据就不开放资源引用；不从回复或素材显示名填白名单。自动适配不写 `pose`、原生未知 `face`、`toggles` 或缺少几何证据的 `framing`，触摸区只可复制报告里非 default 来源的既有坐标。原来磁盘上的适配表与 character.json 不被后台迁移；显式重新适配会重新校验。

完整模式页面接线、效果测量、截图验收和最多三轮调度仍由主线实现。详见 [C906 接线与边界](companion-adapt-contract.md)。
