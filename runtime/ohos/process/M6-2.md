# M6-2：空选择、遍历错误与外部忽略配置

## 结论与精确范围

本后继以已收 43 的进程实现为基准；搜索源前像仍为 `rg.mjs` `1a03c459add86c5aafa236975e1e10bf6f83b079c131016a9ee99b2225403903`、`rg-select.mjs` `23abbb07fc24a036cc75365bd898a22585bafaf70e339291ad6414f6611042be`。它保留 M6-1 对真实 `.git` 文件的处理、M4-3 的单行预算和 M4-4a 的会话授权边界。DSH 固定为 `0.2.1-rc.4`，Node 固定为 `24.22.1`。

先与随包 ripgrep 15.0.0（rev `3a612f88b8`，SHA256 `193906679498de4d939345b937fa24e0e69a03c244bd70c859f5e41232713f21`）测量，再作如下变化：

| 场景 | 实际原生行为 | 本项处理 |
| --- | --- | --- |
| 未显式给路径，空目录或过滤后没有文件 | exit 2，stderr 提示没有搜索文件 | 原 exit 2 已正确；将 stderr 对齐固定原生的两行文字 |
| 显式给 `.`，相同空选择 | exit 1，stderr 为空 | 保留原行为，不一概改成 exit 2 或成功 |
| 访问目录/文件发生真实 EACCES，其他文件可读且命中 | exit 2、错误诊断，同时保留可读匹配 | 保存已选文件；目录错误后继续其余目录，读取错误后继续其余已选文件；整体仍为 2 |
| 虚拟端的遍历检查/候选文件数量预算耗尽 | 原生没有受到这两个私有预算的约束，不能构造“同名原生上限”的等价结论 | 保留预算，返回已选文件的匹配、明确“不完整”诊断与 exit 2，不能伪装完整成功 |

这修正了追加10中“空选择报错即与 rg 不同”的事实前提：是否明确给了路径会改变原生结果。没有因题面概括而改掉本来正确的退出码。

## 部分输出与错误状态

选择器对本地预算使用独立 `SelectionLimitError`，在停止遍历时保留候选列表。普通文件系统错误按明确的 errno 代码或既有 FS 错误前缀识别，累积诊断；其他编程错误、正则/规则错误仍按原失败路径处理。JSON 搜索会处理已保存的候选文件，不再把选择阶段 exit 2 的 NUL 路径列表直接交给消费者；最终 stdout 始终是已形成的 match JSON 记录。

文件读取阶段的同类 IO 错误也保留已有匹配并继续可读文件。只要选择或读取阶段出现错误，最终 exitCode 就是 2，即使 stdout 非空；没有将不完整结果误报为成功或 noMatches。实测了权限失败出现在排序前后两个位置，以及目录/文件两种失败对象。测试以实际降权 UID 和真实 chmod 产生 EACCES，没有注入此错误。

`maxGlobOperations` 与 `maxArrayElements` 的既有值没有改变。前者在进入目录和检查目录项时计数，后者约束保存的候选文件数量；它们不是原生 rg 的选项，也不是实际系统调用次数或总 RSS 上限。一次 `readdir` 及其公开 FS fallback 的 lstat 批次仍可能取得整个目录，本项不宣称预算能阻止这一批次的分配。测试把预算缩小以命中边界，未假装真的创建了一百万个文件。

固定 DSH 的 `runRipgrep` 对非 0/1 仍抛 `SEARCH_FAILED`，不会把 exit 2 的部分 stdout 作为正常 grep 结果展示。原生 rg 遇到同样的权限错误也走这个 DSH 失败分支。因此这里修的是底层输出/失败合同，不宣称聊天中的正常搜索卡片会展示所有部分结果。没有改原 DSH 的成功判定。

M4-3 的 4 MiB 单行预算、64 MiB 输出预算、UTF-8/BOM/CRLF 与二进制拒绝边界保持；单行/输出等其他失败路径没有被改造成完整流式搜索。原生 `--debug` 仅用于宿主测量外部规则读取，尚不在虚拟 rg 的参数清单中；本项没有增加这一能力。

## 外部忽略规则：实测修正“只会多”

鸿蒙端仍不读取授权根外的全局 gitignore 或 `core.excludesFile`。本项在真实 grep 工具的 description 中只对 OpenHarmony/显式进程内仿真追加一句：

> 鸿蒙本机不读取全局 gitignore 或 core.excludesFile；外部排除和反向放行规则均不参与，结果可能与桌面不同。

这个措辞同样是对追加10事实前提的测量修正，并非扩大权限。原生 rg15 在隔离 `XDG_CONFIG_HOME/git/config` 指向的外部文件中：

- `ordinary.txt` 规则会额外排除普通文件；未读取它的虚拟端会多返回该文件。
- `!.hidden` 会反向放行隐藏文件；未读取它的虚拟端仍遵守默认隐藏规则，因而少返回该文件。

两种情况都用真实 Git 仓库和原生 `--debug` 的 `opened gitignore file` 记录确认读取了指定文件。最初仅设置 `GIT_CONFIG_GLOBAL` 的控制没有产生预期排除，作为无效正对照保留，未用它支撑结论。任何无条件“只会多，不会少”的承诺都超出了这次实测事实。

真实 Cordis/ToolRuntime 注册测试证明：普通显式 marker、严格 O0、单独模拟 OH 平台三种正例出现该句；模拟 Android/普通 Linux 即使带旧 `DSH_GO_OHOS_SIM=1` 也不出现。原说明部分、工具名与 schema 保持一致。这些平台覆盖是 Linux 上的门控试验，不是 Android/OH 真机运行。
