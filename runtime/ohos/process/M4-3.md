# M4-3：JSON 搜索的大行预算与单次文件读取

## 结论与适用范围

本包修复 **OHOS 虚拟 rg 的 JSON 搜索路径**中两个已实测的问题：显式文本文件为二进制预检和搜索各读取一次；多十 MiB 的单行在 `Array.from(line)` 展开时可能耗尽 worker 的 V8 堆。现在同一文件操作数只读取一次，在同一份字节上判断二进制、验证 UTF-8 和搜索；超过 **4,194,304 字节（4 MiB）**的搜索行在数组展开前明确返回 exit 2。

作者已在固定 Linux / Node 24.22.1 上运行新 12 项测试的 JIT 与严格 O0 两组、原 Android 3 项 / JIT 49 项 / 严格 49 项，以及原 93 项 rg 差分的两组，均通过，0 skip / TODO。独立审查结果另附，作者结果不代替独审。没有 OpenHarmony 真机数据。

本后继差分以已审 M4-1 v2 为前置：完整补丁 SHA256 `f35040f71b5306b7194514c35e8adc4fcedc11db102df71053eb99749610aac7`，或能产生逐字相同源码的 v1 后继 `fef740e1fbd694004faf8fd1efc0f9ffba5ac7163ac469c902b36ea3c60e1678`。前像 `rg.mjs` SHA256 为 `75a093989ad2d2807a3a725a60d9f67b10853eac0450038a10a81b8cdbdf3e02`。干净 c0949d6 尚无这些 O4 文件，须使用主包提供的完整装配路线，不能把本增量单独应用到空基底。

只改 `rg.mjs`，新增本文、实际测试和测量入口。没有改 runtime / filesystem、M4-2 并发、M4-4 根规则、厂商 diff / pins、Android、依赖锁、RE2JS 源差分或生成产物，也没有覆盖共享 README。M4-1 文档中关于大行和双读的历史待办，在本文所述 JSON 范围内由本包接替。

## 先失败证据

旧实现的严格 O0 探针通过真实受限 `IFileSystem` 读取小型文本，只在公开 `readFileBuffer` 调用前计数，不模拟文件内容。显式 `text.txt` 的记录为两次；显式二进制和 `--text` 各一次。`before-read-count.json` 保留所有返回值和当时源码哈希。

另一次隔离运行使用 48 MiB 全 `a`、无 LF 的文件，模式为不命中的 `z`。输入 SHA256 是 `fcaf3b489c7a30d4914c93ef4cb4cb7e5e59acd52a68285effc8ab9f1d793d92`。采用已有 256 MiB worker old-generation 配置和原 64 MiB 输出预算，加载严格 O0；没有缩小堆、输出或样本来制造反例。

| 运行对象 | 同一 48 MiB 输入的实际结果 |
| --- | --- |
| M4-1 v2 原实现 | V8 报 `Reached heap limit` / `JavaScript heap out of memory`；整个隔离 Node 进程 SIGABRT，shell 退出码 134，未执行最终 JSON 输出。 |
| 固定原生 rg 15.0.0 | 正常 exit 1，匹配数 0，搜索字节 50,331,648。 |
| 本候选 | 正常 exit 2、signal null、stdout 空；stderr 明确列出预算和实际行字节；下一次虚拟任务仍成功。 |

因此新结果是**明确的支持边界**，不是声称原生 rg 也无法搜索该文件。不能把它转换成 exit 1 / `noMatches`。真实 DSH `buildGrepCommand → runRipgrep` 已验证会将其传播成 `SEARCH_FAILED`。

旧进程在 `finally` 前死亡，故首份 `before-48mib-strict.json` 本来就是空文件；没有补造进程内报告。外层实际 exit 134、完整 stderr、当时夹具源码哈希和输入事实记录在 `before-48mib-result.json`。随后只在核对本次唯一夹具的精确路径、inode、内容和子项后清理残留。新版测量入口支持 `M4_LARGE_PRE_REPORT`，在启动 worker 以前写出准确自有路径，便于宿主在未来的崩溃复现后收尾。

## 实现与预算定义

### 单次读取

JSON 路径不再先执行独立的完整二进制预检。分类阶段只做路径 metadata；正式搜索每个操作数调用一次 `ctx.fs.readFileBuffer`，同一返回值用于二进制判断及文本搜索。

`IFileSystem.readFileBuffer` 的公开返回类型为 `Uint8Array`。通过 `Buffer.from(content.buffer, content.byteOffset, content.byteLength)` 建立同一 backing store 的视图，避免原 `Buffer.from(content)` 再复制整个文件。新测试故意返回具有非零 `byteOffset`、前后填有非法字节的真实内容视图，以验证只使用规定的字节范围。

默认显式二进制仍 exit 2 并提示 `--text`；遍历选择的二进制仍跳过；显式 `--text` 保留 NUL。Node 公开 `node:buffer.isUtf8` 取代仅为验证而创建整文件字符串的 `TextDecoder.decode`，非法 UTF-8 仍明确 exit 2，不用 replacement character 继续搜索。未绕过受限 FS，未引入宿主文件读取通道。

这里的“一次”按一次文件操作数计。如果调用者重复显式传同一个路径，或多个输入根重叠，本包没有做新的去重，不宣称全调用范围仅访问该物理 inode 一次。ignore 文件的读取属于选择器规则，不算正文预检和搜索的重复读。

### 单行预算

预算为**经文件首 BOM 处理后的 UTF-8 字节数**：不包括 LF；CRLF 中 CR 仍是行的一部分，计入预算；仅文件最前一枚 UTF-8 BOM 不计入。后续 BOM、组合附标、多字节字符都按实际字节计量。

先用 Buffer 的 LF 查找得到行起止，再检查长度，最后才调用 `Array.from(line)`。4 MiB 恰好允许，4 MiB + 1 明确拒绝，不依赖模式是否会匹配。文件后部出现超长行时，不返回已经积累的半份匹配结果；整个搜索 stdout 为空、exit 2。

4 MiB 的选择限定了单次数组展开至 4,194,304 个元素，避免原反例的 50,331,648 个元素。已实际测得：4 MiB 的 ASCII 命中行完整输出；含中文的恰好字节边界完整输出；BOM / LF / CR 边界符合定义；6 MiB 以上、各行在预算内的文件完整输出。仍保留既有 **64 MiB 文件读取上限、64 MiB JSON 输出预算和解释器匹配数预算**，没有靠缩小输出截断来“通过”。

单次严格测量中，4 MiB 未命中样本约 1.13 秒、整个隔离进程 maxRSS 251,816 KiB；48 MiB 拒绝约 1.11 秒、maxRSS 297,360 KiB。RSS 包括宿主、输入创建、worker 与外部字节存储，**不是** worker old-generation 的占用，也不是手机内存结果；两个数不作为速度对比或最优阈值证明。256 MiB worker 参数本身不限制整个进程 RSS。行预算只修复这里的输入展开风险，不证明任意正则、全部输出组合或任意并发下均不可能耗尽内存。

## 重现命令

先按 M4-1 的固定依赖和构建步骤准备对应源码树。以下三个路径变量由调用方给出绝对路径，Node 固定 24.22.1：

```bash
NODE=/Node24.22.1/bin/node
PROCESS_PREFIX=/已应用O4a和marker的DSH-prefix
SIM_PRELOAD=/已审M3-3/runtime/ohos/sim/preload.mjs

"$NODE" runtime/ohos/process/build-rg-regex.mjs /含esbuild0.27.3的prefix
OHOS_TEST_PROCESS_PREFIX="$PROCESS_PREFIX" \
  "$NODE" --import ./runtime/ohos/sim/marker.mjs --test --test-isolation=none \
  runtime/tests/ohos/process-rg-large.test.mjs
OHOS_TEST_PROCESS_PREFIX="$PROCESS_PREFIX" \
  "$NODE" --jitless --import "$SIM_PRELOAD" --test --test-isolation=none \
  runtime/tests/ohos/process-rg-large.test.mjs

"$NODE" --import ./runtime/ohos/sim/marker.mjs runtime/tests/ohos/process-rg-m4-differential.mjs
"$NODE" --jitless --import "$SIM_PRELOAD" runtime/tests/ohos/process-rg-m4-differential.mjs
```

原 `runtime/ohos/process/test.sh` 的完整命令与 M4-1 相同，设置 `OHOS_TEST_BASE_PREFIX`、`OHOS_SIM_PRELOAD`、`OHOS_ESBUILD_PREFIX` 后运行。本包没有修改该共享脚本，新 12 项入口如上单列，避免把已跑旧套件误报成自动包含新测试。

单独重现读取计数或 48 MiB 测量：

```bash
M4_LARGE_MODE=reads "$NODE" --jitless --import "$SIM_PRELOAD" \
  runtime/tests/ohos/process-rg-large-probe.mjs

M4_LARGE_PRE_REPORT=/自有目录/before-worker.json \
  "$NODE" --jitless --import "$SIM_PRELOAD" \
  runtime/tests/ohos/process-rg-large-probe.mjs
```

探针和新测试均支持 `M4_PROCESS_ROOT=/待测runtime/ohos/process` 指向独立应用树。若将 48 MiB 探针指向旧冻结 v2，已知会杀死整个该 Node 进程，应由独立宿主进程启动；崩溃前记录所标的确切自有夹具可由宿主核对后清理，不能扫描前缀删除其他任务文件。生成物不入源码补丁。

## 明确保留的范围

本包没有重写非 JSON 的 `ctx.origCommand` 路径。该公开 API 只收 argv，仍保留旧二进制预检和 bundled 命令执行；因此不宣称非 JSON 正文也只有一次读取，或已获得这里的行预算。JSON 路径也仍整文件读取，受原 64 MiB FS 上限约束，不是流式读文件实现。

M4-1 先前列出的非 JSON Unicode / include、复杂 `--files`、全局 ignore、非 UTF-8 搜索等未支持范围继续存在。本包不更改 M4-2 / M4-4 的并发和授权判断；目标 OHOS ABI、设备文件系统和手机峰值内存仍待实际验证。
